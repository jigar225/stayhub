# StayHub backend after M2.1

The HTTP adapters are `app/auth_routes.py` and `app/listing_routes.py`. They validate request schemas, extract bearer credentials/refresh cookies/CSRF header values, enforce exact trusted Origin and HTTP-only JSON/Fetch Metadata rules, invoke one complete service operation and apply response cookies. `main.py` composes routers and error/request/health handling. Route handlers contain no SQL, commit/rollback, listing publication rules, photo state changes or session-rotation workflow. Listing mutations and Host enrollment accept an optional zero-argument transport guard: the adapter supplies its Origin/body check, and the operation invokes it immediately after its live role/ownership check at the original position. This preserves mixed-invalid-request error precedence and existing row-lock timing without duplicate auth reads. The service knows no HTTP types or header names; direct trusted callers omit the guard. Guard failures roll back the operation normally. Handler names and schemas remain unchanged, so OpenAPI remains byte-equivalent after canonical JSON serialization.

`auth_service.py` owns registration, login, CSRF bootstrap, refresh rotation/reuse revocation, logout, profile, additive Host enrollment and role-probe operations. Cryptographic decoding creates a frozen `AccessContext(user_id, session_id, expires_at)` without SQL; it cannot leave an autobegun transaction before the operation. Every authenticated operation reloads current session/account/roles inside its transaction and checks access and absolute session expiry. A context is an internal verified credential value, not browser-supplied identity. Pure password, token-digest, HMAC and role helpers live in `security.py` alongside clearly HTTP-only origin/cookie helpers. No service accepts a FastAPI Request or Response, sets cookies, reads headers or performs Origin checks.

`listing_service.py` exposes complete create/list/get/update/publish/unlist/upload-intent/complete/delete/order/read operations. Each checks current Host membership and owner identity internally; callers cannot bypass ownership by skipping a route guard. Private helpers perform validation, row locking, output projection and internal photo state transitions without committing. SQLAlchemy is used directly; there is no repository or generic service framework. The existing Pydantic models are validated domain inputs and detached result snapshots, not ORM objects escaping transaction scope. `ApiError` remains the small existing error-data type (status/code/message/field errors); it has no HTTP side effects, and `main.py` renders its envelope.

Every public database operation takes an **idle SQLAlchemy Session** and owns a `with db.begin()` boundary. Success commits; ordinary failure rolls back. An already active caller transaction is rejected by SQLAlchemy rather than silently committed, rolled back or wrapped in a savepoint. Reads also end their transaction before returning. Result snapshots are built after required flushes and before commit, so expiration/lazy loading cannot silently start a second transaction afterward. Retained identity maps are refreshed on auth and locked listing/session queries; direct callers using `expire_on_commit=False` still observe current versions/revocation. Request-scoped sessions continue to come from the unchanged `db.py` dependency. To call services directly, create `with Session(get_engine()) as db`, call the operation and reuse the now-idle session for the next operation.

Refresh locks the session, rereads refresh consumption after obtaining the lock and checks the supplied CSRF **value against that locked session's hash** using a pure constant-time helper. Header extraction and HTTP error rendering remain in the adapter; moving the value comparison outside the lock would introduce a security race. Successful rotation consumes/inserts history atomically. Consumed-token reuse and inactive-account cases return an explicit `RefreshFailure` **after** the transaction exits and commits revocation. Only then does the adapter render401. Raising that failure within `begin()` would roll back the revocation; direct Postgres tests verify the committed postcondition independently. Response refresh-cookie updates occur only after the service succeeds.

Storage stays in the unchanged `storage.py` adapter. Photo completion holds the listing lock through bounded download/decode/re-encode and final-object write, then commits verified metadata. Final keys remain independent and immutable relative to staging authorization. A successful object write followed by a failed DB commit leaves an unreferenced orphan for the existing conservative cleanup; it never returns a successful attachment. Completion retries retain photo identity/order/version. Deletion commits authoritative database removal first, then attempts external deletes; failure remains the existing cleanup backlog. `storage_setup.py`/`storage_cleanup.py`, explicit seeds, migrations, persistence models, configuration, dependencies and schema are unchanged in M2.1.

Verification retains all33 real PostgreSQL/S3 M1/M2 tests and adds focused direct-service regressions for transaction ownership, role/owner/version checks, refresh reuse committed before failure, CSRF/logout rollback, access expiry and stale retained ORM state. Coordinator evidence records final root/static/browser checks, exact OpenAPI equality and unchanged schema/dependency/storage/frontend hashes. No UI or M3 feature was added.


## M3 additions

`calendar_routes.py` and `discovery_routes.py` remain thin HTTP adapters. `calendar_service.py` owns complete authenticated owner calendar read/create/remove operations with an idle-Session transaction per call. Mutations lock the listing, recheck current Host membership/ownership, then apply the transport guard. PostgreSQL's partial GiST exclusion constraint on active `calendar_entries` is the final overlap authority, including for future reservation occupancy. Removal marks a block inactive. Blocks leave listing content versions unchanged.

`discovery_service.py` owns published-only browse/detail/availability/photo-renewal operations and public projection. SQL applies publication, literal destination matching, capacity, occupancy and local-date bounds before bounded UUID keyset pagination. Shared `pricing.py` checks local scheduling, capacity, request lead-time and availability and creates integer-cent signed quotes; bounded post-page scheduling filters may yield an empty page with a continuation cursor. `date_rules.py` centralizes local-date/range/DST behavior; `business_time.py` supplies aware business UTC without altering auth clocks. Quote reads own one transaction and make no reservation or other state change. Public image signing uses the existing external `storage.py` adapter.

`seed_content.py` is an explicit trusted application caller, not an HTTP route or startup hook. It authenticates the existing demo Host and calls complete listing/photo/publication operations using separate idle-Session boundaries; it never wraps those operations in a nested transaction. Small independent tracking transactions record `DemoImport`/`DemoAssetPhoto` progress and lock the import marker for expected-version reconciliation; listing mutations retain their service-owned listing locks. Completed imports skip modifications; interrupted imports preserve changed versions and resume only safely missing assets. A source upload is unverified until the existing photo-completion operation validates/re-encodes it. Object-store and DB failures retain the M2 orphan/retry semantics rather than pretending to share a distributed transaction.

Migration `0003_calendar_demo` is additive; M1/M2 endpoint paths, existing schemas and auth/session transport semantics stay compatible. No persistence volume is removed. Current verification is in `docs/m3-evidence.md`; the preceding sections describe the M2.1 baseline.

## M4 atomic booking and requests

`booking_routes.py` is a thin adapter for Pay, party reads, Host Today and host decisions. It derives the existing cryptographically verified AccessContext, forwards transport guards and the original Idempotency-Key, and translates a CommittedFailure only after the service transaction has committed. `booking_service.py` owns each complete Pay/decision transaction and returns immutable Pydantic snapshots. `booking_quotes.py` decodes/validates quotes and current terms without a transaction; `booking_ledger.py` projects booked data and appends state/money events/refunds within its caller's transaction. `booking_queries.py` owns authorized read transactions; GET never expires requests. No public transactional service is nested inside another.

Mutations read current session/account/roles, acquire a transaction-scoped advisory try-lock for actor+operation+key, resolve successful replay, lock listing, then lock existing reservation. Calendar block mutations use the same listing-before-entry order. Expiry scans a bounded candidate page, closes that read transaction, then processes one listing/reservation per transaction and rechecks deadline. It does not hold multiple listing locks. Duplicate sweeps and host decisions cannot create duplicate refunds or reverse a terminal state. Lock contention/deadlock victims receive explicit retry guidance; all writes roll back together. `expire_requests` CLI/periodic worker invokes this same operation and can wait for database/migrations on local startup.

The additive 0004 migration retains the existing occupancy GiST exclusion, adds the actual reservation FK and one occupancy entry per reservation, and creates reservations/payments/refunds/idempotency_records/event_log. Composite monetary foreign keys enforce charge=booked total and M4 full refund=original charge; money identities and per-reservation uniqueness are additionally constrained. Policy rule data, listing summary, house rules, price and UTC/local schedules are copied at Pay. Current listing edits/unlisting cannot rewrite party records. Parties may obtain signed currently verified photos through their reservation endpoint after unlisting; public photos remain published-only. Deleted photos need not remain available.

Quote verification pins HS256, issuer, audience and purpose and validates a complete typed claim schema. Business-time iat/exp checks are explicit (real-time JWT timestamp verification is disabled only for booking quotes). Revalidation uses one captured locked-decision business timestamp for local-date and scheduled-time eligibility. Security/session/photo URL clocks are untouched. Idempotency stores a SHA256 normalized input fingerprint and original successful status/body, never full quote tokens. Authentication/live role checks precede replay; successful replay precedes quote expiry/current-state checks. Event payloads contain only sanitized state/amount/record references; business timestamps and real recorded timestamps are separate. M4 computes future entitlement but does not create/release payouts, cancel stays, expose event UI or advance time.

## M5 refunds, progression and persisted business time

`refunds.py` is pure booked-definition arithmetic with elapsed UTC cutoffs and integer half-up cents. `cancellation_service.py` owns preview and atomic cancellation transactions, using signed actor/state/financial-version/amount claims and rechecking after listing/reservation locks. Refund, occupancy release, effective entitlement, payout update, events and successful idempotency response commit together. Original charge/price/policy/rule snapshots remain history. Pending overdue cancellation/preview preserves committed expiry before rejecting the operation.

`financial_routes.py` remains transport-only. `financial_queries.py` owns host payout/earnings and Admin audit read transactions. Earnings aggregates include the host's whole ledger independently of the visible page/filter. Party outputs add financial version, original/effective fee distinction and payout; historical M4 idempotency replay uses the stored raw JSON through `wire_result`, bypassing response-model default expansion while preserving original HTTP status.

`business_time.at(db)` reads the singleton offset inside an existing caller transaction without nesting; `now()` uses an independent read connection for callers without a Session and never caches the offset. Missing singleton fails closed. Auth/session tokens, S3 signing, limiter and event recorded_at still use real time. `clock_service` advances the locked offset/version with an audit event/idempotency response in one transaction, commits, then invokes sweep separately. Replaying keeps the original clock snapshot and safely resumes work; a sweep failure cannot undo or repeat advancement. Demo mutations require live Admin, trusted Origin, DEMO_MODE and positive bounded integer seconds. No reset/backward operation exists.

`sweep.py` scans a bounded due candidate page then locks one listing→reservation→payout per transaction. It repeatedly chooses the next effective event ordered timestamp then expiry/check-in/checkout/payout. Pending never enters a stay. Completed historical occupancy remains active; retained cancellation payouts use the original due time. Payout release identity and unique audit action/target prevent duplicate releases under overlap/retry; crashes roll back the whole reservation transaction. Deferred contention is reported with has_more. The old expire_requests operation/CLI remains compatible, while the periodic worker uses unified sweep.

Migration0005 deliberately replaces the M4 full-refund amount FK with the original-charge-bound composite reference plus partial component checks. State-specific normal/terminal entitlement checks remain; cancelled payouts cannot carry nonzero net. It adds/backfills one held/scheduled/cancelled payout per M4 reservation and a zero-offset singleton, with no releases/events/history/idempotency rewrites. Financial downgrade is rejected because partial refunds/releases cannot safely be represented by M4 constraints.
